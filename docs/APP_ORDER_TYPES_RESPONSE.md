# پاسخِ بک‌اند — «نوع خدمت» بر اساسِ دستگاه و استان

**به:** تیم اپ مشتری — **موضوع:** فیلترِ نوعِ خدمت (`available_order_types`)

## انجام شد ✅
فیلدِ `available_order_types` به هر دستگاه در پاسخِ کاتالوگ اضافه شد:

```
GET /v1/customer/services/categories?city_id=N   (یا ?state_id=P)
{
  "data": [
    { "id": 3, "name": "یخچال", "slug": "fridge", ...,
      "available_order_types": ["repair", "service"] }   // ← جدید
  ]
}
```

## منطق (استان‌محور، مثلِ خودِ کاتالوگ)
- مبنا `state_id` (یا استانِ `city_id`) است.
- برای هر دستگاه، `available_order_types` = **اجتماعِ `service_types`ِ تکنسین‌های
  فعالی** که در آن استان همان دستگاه را پوشش می‌دهند.
- مقادیرِ ممکن از جدولِ `crm_service_types` می‌آید (پیش‌فرض: `repair`, `service`,
  `install`) و خروجی به همان ترتیبِ استانداردِ نوع‌ها مرتب است.

## قاعده‌های لبه (تا نوعی به‌اشتباه حذف نشود)
- تکنسینِ **همه‌کاره** (بدونِ تگِ دستگاه) → نوع‌هایش روی همهٔ دستگاه‌ها اعمال می‌شود.
- تکنسینِ بدونِ `service_types` (داده‌ی legacy) = «همهٔ نوع‌ها را ارائه می‌کند».
- والدِ ادغامی و اجزایش (مثلِ گاز = اجاق‌گاز + گاز رومیزی) نوع‌ها را دوطرفه
  به‌اشتراک می‌گذارند.
- اگر برای دستگاهی هیچ نوعِ مشخصی به‌دست نیامد، **همهٔ نوع‌ها** برمی‌گردد (محدود
  نمی‌کنیم).

## سازگاریِ عقب‌رو
- اگر **استان مشخص نباشد** یا **دادهٔ پوشش کامل نباشد** (`coverage_data_complete=false`)
  یا جدولِ نوع‌ها در دسترس نباشد → `available_order_types` = **همهٔ نوع‌ها**؛ یعنی
  اپ مثلِ قبل همه را نشان می‌دهد.
- فیلد همیشه حاضر است؛ اگر آرایه شاملِ یک نوع نبود، آن نوع در آن استان ارائه
  نمی‌شود و اپ باید مخفی‌اش کند.

## کارِ اپ
به‌محضِ دریافتِ `available_order_types`، مرحله‌ی «نوع خدمت» را بر اساسِ آن فیلتر
کنید. نوعِ غیرموجود نمایش داده نشود.

## نکتهٔ عملیاتی (سمتِ ما)
دقتِ این فیلد به کاملیِ `service_types`ِ تکنسین‌ها بستگی دارد. تکنسین‌هایی که
`service_types`شان خالی است «همه‌کاره» فرض می‌شوند؛ برای فیلترِ دقیق‌تر باید
`service_types`ِ تکنسین‌ها در پنل تکمیل شود.
