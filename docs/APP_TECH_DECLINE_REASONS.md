# قراردادِ بک‌اند — «علت‌های ردِ سفارش» (اپ تکنسین)

**به:** تیم اپ تکنسین · **موضوع:** علت‌های انتخابیِ ردِ سفارش که ادمین تعیین می‌کند

## خلاصه
ادمین از پنل (**تنظیمات عملیات سفارش**) لیستِ «علت‌های کنسل/رد» را مدیریت می‌کند.
این لیست حالا به اپ تکنسین هم می‌رسد تا هنگامِ **ردِ سفارش** (`declined`) به‌جای
متنِ آزاد، تکنسین یکی از گزینه‌های تعیین‌شده را انتخاب کند.

## ۱) دریافتِ گزینه‌ها
از همان `app-config` که اپ هر ~۳۰ دقیقه می‌گیرد:

```
GET /v1/technician/app-config
{
  "success": true,
  "data": {
    ...
    "decline_reasons": ["خارج از تخصص", "آدرس خارج از محدوده", "..."]
  }
}
```

- آرایه‌ای از رشته‌های فارسی، به ترتیبی که ادمین چیده است.
- ممکن است هر زمان تغییر کند؛ همیشه از `app-config` بخوانید (hard-code نکنید).
- قرارداد ادغامِ key-by-key حفظ است؛ اگر کلید نیامد، رفتارِ قبلیِ اپ.

## ۲) ارسالِ علتِ انتخاب‌شده هنگام رد
روی همان endpointِ تغییرِ وضعیت:

```
POST /v1/technician/orders/{id}/status
{
  "status": "declined",
  "cancel_reason": "خارج از تخصص"      // یکی از مقادیرِ decline_reasons
}
```

قواعد:
- اگر `cancel_reason` **از لیست** انتخاب شود، فیلدِ `description` (متنِ آزاد)
  **اجباری نیست**. می‌توانید اختیاری یک توضیحِ تکمیلی هم بفرستید؛ در تاریخچه ثبت می‌شود.
- اگر `cancel_reason` **نفرستید**، مثلِ قبل `description` (حداقل ۱۵ کاراکتر) اجباری است
  (سازگاریِ عقب‌رو برای نسخه‌های قدیمیِ اپ).
- `cancel_reason`ی که در لیستِ ادمین نباشد با **۴۲۲** رد می‌شود:
  `«علتِ ردِ انتخاب‌شده معتبر نیست؛ یکی از گزینه‌های تعیین‌شده را انتخاب کنید.»`

## ۳) رفتارِ ذخیره
- علتِ انتخاب‌شده در فیلدِ سفارش ذخیره و در تاریخچهٔ وضعیت («علت رد: …») لاگ می‌شود.
- همین علت در پنلِ ادمین و در پیامکِ لغو (متغیرِ `{cancel_reason}`) هم دیده می‌شود.

## پیشنهادِ UX
مودالِ ردِ سفارش: یک لیستِ انتخابی (رادیو/دراپ‌داون) از `decline_reasons` + یک فیلدِ
اختیاریِ «توضیح بیشتر». دکمهٔ تأیید تا وقتی یک علت انتخاب نشده غیرفعال بماند.

با احترام — تیم بک‌اند (پنل)
