# قراردادِ بک‌اند — «ردِ سفارش» توسطِ تکنسین (اپ تکنسین)

**به:** تیم اپ تکنسین · **موضوع:** علت‌های انتخابیِ ردِ سفارش + بازگشتِ خودکار به تخصیص

## مفهوم — «رد» ≠ «کنسل»
- **کنسل** (ادمین، پنل): سفارش مرده به حساب می‌آید. ربطی به اپ تکنسین ندارد.
- **رد** (تکنسین، اپ): تکنسین توانایی/صرفهٔ انجام نداشته یا سفارش برایش اعتبار
  نداشته. این علت‌ها **لیستِ جداگانه‌ای** دارند که ادمین مدیریت می‌کند.

## ۱) دریافتِ گزینه‌ها — از `app-config`
اپ هر ~۳۰ دقیقه `app-config` را می‌گیرد:

```
GET /v1/technician/app-config
{
  "success": true,
  "data": {
    ...
    "decline_reasons": [
      { "label": "عدم توانایی در انجام کار", "reopen": true },
      { "label": "خارج از محدودهٔ کاری من",   "reopen": true },
      { "label": "سایر",                       "reopen": false }
    ]
  }
}
```

- `label`: متنی که در مودالِ رد نشان می‌دهید.
- `reopen`: فقط اطلاع‌رسانی به کاربر است (اختیاری). رفتارِ واقعی سمتِ سرور اعمال
  می‌شود؛ لازم نیست اپ کاری با آن بکند، ولی می‌توانید مثلاً زیرِ گزینه بنویسید
  «این سفارش به تکنسینِ دیگری واگذار می‌شود».
- لیست هر زمان از پنل تغییر می‌کند؛ همیشه از `app-config` بخوانید (hard-code نکنید).

## ۲) ارسالِ رد — روی endpointِ تغییرِ وضعیت
```
POST /v1/technician/orders/{id}/status
{
  "status": "declined",
  "decline_reason": "عدم توانایی در انجام کار"   // یکی از label‌های بالا
}
```

- فیلدِ توصیه‌شده: **`decline_reason`**. برای سازگاری، `cancel_reason` هم پذیرفته می‌شود.
- اگر یک `label` از لیست انتخاب شود، `description` (متنِ آزاد) **اجباری نیست**؛
  می‌توانید اختیاری هم بفرستید (در تاریخچه ثبت می‌شود).
- اگر هیچ علتی نفرستید، مثلِ قبل `description` (حداقل ۱۵ کاراکتر) اجباری است
  (سازگاریِ عقب‌رو).
- `label`ی که در لیست نباشد → **۴۲۲**.

## ۳) دو رفتارِ سرور بر اساسِ `reopen`
- **`reopen = false`** → سفارش «رد شده»ی **نهایی** می‌شود (مثلِ قبل؛ ادمین می‌تواند
  بعداً به «کنسل» تبدیل کند). پاسخ: سفارش با وضعیتِ `declined`.
- **`reopen = true`** → سفارش از شما **گرفته** و برای تخصیصِ تکنسینِ جدید **باز**
  می‌شود (سیستمِ پخشِ خودکار یا ادمین انتخاب می‌کند). شما دیگر مالکِ سفارش نیستید.
  همان تکنسینی که رد کرده، دوباره روی این سفارش پیشنهاد **نمی‌شود**.

پاسخِ حالتِ بازشدن:
```
{
  "success": true,
  "message": "سفارش رد شد و برای تخصیصِ تکنسینِ جدید باز شد.",
  "data": { "reopened": true, "order_id": 123, "status": "new" }
}
```

**اقدامِ اپ:** وقتی `data.reopened === true` است، سفارش را از لیستِ سفارش‌های تکنسین
**حذف/به‌روزرسانی** کنید (دیگر به او تعلق ندارد). در حالتِ نهایی (`reopen=false`)
سفارش با وضعیتِ `declined` می‌ماند.

## پیشنهادِ UX
مودالِ رد: لیستِ رادیو از `decline_reasons` + فیلدِ اختیاریِ «توضیح بیشتر». دکمهٔ
تأیید تا انتخابِ یک علت غیرفعال بماند. برای گزینه‌های `reopen=true` می‌توانید یک
بجِ کوچک «واگذاری به تکنسین دیگر» نشان دهید.
