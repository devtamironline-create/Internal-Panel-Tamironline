# نامه به تیم توسعهٔ اپ مشتری — پرداخت آنلاین فاکتور

**تاریخ:** ۱۴۰۵/۰۵/۲۴ — **از:** تیم بک‌اند پنل — **موضوع:** فلوی کامل پرداخت آنلاین + قرارداد API

## فلوی کامل

```
تکنسین سفارش را تکمیل می‌کند
   ↓ (خودکار، سمت پنل)
فاکتور صادر می‌شود + پیامک با لینک عمومی فاکتور برای مشتری می‌رود
   ↓ در اپ مشتری
سفارشِ تکمیل‌شده دکمهٔ «پرداخت آنلاین» می‌گیرد → باز کردن pay_url
   ↓
صفحهٔ پیش‌نمایش فاکتور (بدون لاگین) → دکمهٔ پرداخت → درگاه (زیبال یا ملت)
   ↓ بعد از پرداخت
callback سمت سرور: تأیید سرور-به-سرور + کنترل مبلغ → فاکتور paid
   → سهم تکنسین خودکار به کیف‌پولش می‌نشیند → پیامک/پوش به تکنسین
   ↓ در اپ مشتری
poll کردن status → UI «پرداخت شد» ✓
```

همهٔ منطق مالی و امنیتی سمت سرور است؛ اپ فقط دو URL را باز/poll می‌کند.

## قرارداد API

کلید همه‌چیز `public_token` فاکتور است — رشتهٔ تصادفی ۴۰ نویسه‌ای غیرقابل‌حدس که در لینک پیامکی هم همان است. اپ آن را از همان کانالی که امروز لینک فاکتور را می‌گیرد بردارد.

### ۱) باز کردن پرداخت

```
GET https://panel.tamironline.com/crm/pay/{public_token}
```

- صفحهٔ پیش‌نمایش فاکتور + دکمهٔ پرداخت. در **مرورگر خارجی یا Custom Tab** باز کنید، نه WebView داخلی — درگاه‌های بانکی داخل WebView مشکل‌سازند و برگشت از درگاه هم در مرورگر تمیزتر است.
- حالات خطا خودِ صفحه هندل می‌کند: قبلاً پرداخت‌شده، لغوشده، مبلغ صفر (نیازی به پرداخت ندارد)، فاکتور جایگزین‌شده (پیام راهنما)، درگاه تنظیم‌نشده.

### ۲) وضعیت پرداخت (برای UI اپ)

```
GET https://panel.tamironline.com/crm/pay/{public_token}/status
```

پاسخ 200:

```json
{
  "success": true,
  "data": {
    "invoice_code": "INV-2608-01234",
    "amount": 2000000,            // تومان
    "status": "issued|paid|cancelled",
    "paid": false,
    "paid_at": null,              // ISO8601 بعد از پرداخت
    "superseded": false,          // true = این فاکتور جایگزین شده؛ لینک جدید لازم است
    "payable": true               // فقط وقتی true دکمهٔ پرداخت را نشان دهید
  }
}
```

- توکن ناشناخته → **404** با `{"success": false}`.
- **rate limit: ۳۰ درخواست در دقیقه** به‌ازای هر IP — بعد از برگشت مشتری از درگاه هر ۳ ثانیه یک‌بار و حداکثر ~۱ دقیقه poll کنید؛ بعد از آن یک دکمهٔ «بررسی مجدد» دستی کافی است.
- منبع حقیقت `payable` است — منطق «پرداخت‌پذیر بودن» را در اپ بازسازی نکنید.

### ۳) چه زمانی دکمهٔ پرداخت نشان داده شود

- سفارش تکمیل شده و فاکتور دارد → یک‌بار `status` را بگیرید؛ اگر `payable=true` دکمه را نشان دهید.
- `paid=true` → بج «پرداخت شده» + لینک رسید (همان لینک عمومی فاکتور که دارید).
- `superseded=true` → این لینک کهنه است (سفارش برگشتی دوباره تکمیل شده)؛ آخرین لینک فاکتور را نمایش دهید.

## چند نکتهٔ پشت‌صحنه (فقط برای اطلاع)

- تأیید پرداخت سرور-به-سرور است و **مبلغ تأییدشدهٔ درگاه با مبلغ فاکتور تطبیق داده می‌شود** — callback جعلی یا دست‌کاری‌شده هیچ اثری ندارد.
- callback تکراری (redirect + webhook همزمان) با قفل ردیف idempotent است — نه فاکتور دوبار paid می‌شود نه واریز تکراری رخ می‌دهد.
- درگاه فعال (زیبال/ملت) تنظیم پنل است و برای اپ شفاف — همیشه همان `pay_url` را باز کنید.
- رسید عمومی فاکتور هم حالا دکمهٔ «پرداخت آنلاین» دارد؛ مشتری از لینک پیامک هم می‌تواند مستقیم بپردازد.

## به‌روزرسانی ۱۴۰۵/۰۵/۲۵ — برگشت خودکار به اپ بعد از پرداخت

مشکل گزارش‌شده: مشتری بعد از پرداخت در صفحهٔ نتیجهٔ پنل می‌ماند و به اپ برنمی‌گردد. حل شد:

### قرارداد `return`

موقع باز کردن صفحهٔ پرداخت، لینک برگشت اپ خودتان را بدهید:

```
https://panel.tamironline.com/crm/pay/{public_token}?return={URL-encoded deep link}
```

مثال: `?return=tamironline%3A%2F%2Fpayment-result%3Forder%3D5512`

- بعد از پرداخت (موفق یا ناموفق)، صفحهٔ نتیجه **۳ ثانیه بعد خودکار** به همان لینک برمی‌گردد + دکمهٔ «بازگشت به اپلیکیشن» برای کلیک دستی.
- سرور این پارامترها را به لینک شما اضافه می‌کند: `payment=success|failed` و `reference={شماره پیگیری}`.
- **امنیت**: لینک برگشت از allowlist عبور می‌کند — الان `tamironline://` و `karbalad://` و زیردامنه‌های `app.tamironline.com` مجازند (فقط https). اگر scheme یا دامنهٔ دیگری لازم دارید اعلام کنید تا در پنل اضافه شود؛ لینک غیرمجاز بی‌سروصدا حذف می‌شود (پرداخت کار می‌کند ولی برگشت خودکار ندارد).
- منبع حقیقت نهایی همچنان `GET /crm/pay/{token}/status` است — بعد از برگشت به اپ آن را یک‌بار چک کنید (پارامتر `payment` فقط برای UI فوری است، نه تصمیم مالی).

## چک‌لیست اپ

- [ ] دکمهٔ «پرداخت آنلاین» روی سفارش تکمیل‌شده وقتی `payable=true`
- [ ] باز کردن `pay_url` در مرورگر/Custom Tab (نه WebView)
- [ ] poll وضعیت بعد از برگشت به اپ (هر ۳ ثانیه، حداکثر ~۱ دقیقه) + دکمهٔ «بررسی مجدد»
- [ ] حالت‌های `paid` / `superseded` / `cancelled` در UI
- [ ] هیچ منطق مبلغ/کارمزدی در اپ — فقط `amount` نمایشی

## ضمیمه — پاسخ به گزارش پیاده‌سازی اپ (۱۴۰۵/۰۵/۲۵)

پیاده‌سازی‌تان با قرارداد منطبق است. پاسخ تنها ابهام:

1. **تأیید می‌شود:** `payment.payment_url` دقیقاً `https://panel.tamironline.com/crm/pay/{public_token}` است (صفحهٔ پرداخت پنل — نه URL مستقیم درگاه). استخراج آخرین segment درست کار می‌کند.
2. **و گزینهٔ «بهترین» هم انجام شد** — از این نسخه بلوک `payment` در پاسخ `GET /v1/customer/orders/{id}/invoice` دو فیلد صریح دارد:
   - `public_token`: **همیشه** موجود است، حتی برای فاکتور paid/cancelled — تا poll کردن `/crm/pay/{token}/status` بدون استخراج URL ممکن باشد.
   - `pay_url`: فقط وقتی فاکتور قابل پرداخت است (همان `payment_url`؛ فیلد قدیمی برای سازگاری حذف نشده).

   بعد از دیپلوی بعدی پنل، منطق fallback شما خودکار سراغ فیلد صریح می‌رود.
3. return با `https://app.tamironline.com/...` تأیید است (در allowlist)؛ هر وقت scheme سفارشی خواستید اعلام کنید.

## به‌روزرسانی ۱۴۰۵/۰۵/۲۶ — رفع باگ دکمهٔ پرداخت + مسیر یک‌کلیکه

- **باگ گزارش‌شده رفع شد**: دکمهٔ پرداختِ صفحهٔ preview به‌خاطر کش‌شدن صفحه (توکن CSRF مرده) کاربر را به همان صفحه برمی‌گرداند. POST از CSRF مستثنا شد (حفاظ = خودِ public_token) و همهٔ مسیرهای پرداخت هدر no-cache گرفتند.
- **فیلد جدید `payment.direct_pay_url`**: مسیر یک‌کلیکه — کاربر بدون دیدن صفحهٔ پیش‌نمایش و کلیک دوم، مستقیم به درگاه می‌رود:

```
GET https://panel.tamironline.com/crm/pay/{token}/go?return={encoded}
```

توصیهٔ ما: دکمهٔ پرداخت اپ را به `direct_pay_url + ?return=` وصل کنید (تجربهٔ یک‌کلیکه). `pay_url` برای وقتی است که بخواهید مشتری اول فاکتور را ببیند. حالت‌های خطا (پرداخت‌شده/لغو/صفر/درگاه خاموش) در هر دو مسیر صفحهٔ خوانا دارند و `payable=true` همچنان شرط نمایش دکمه است.

هر ابهامی بود همین‌جا پاسخ می‌دهیم. — تیم بک‌اند

## به‌روزرسانی ۱۴۰۵/۰۵/۲۸ — سفارشِ بسته‌شده دیگر درگاه ندارد

اگر سفارشی **بدونِ انجامِ کار** بسته شود (لغو، ردِ سفارش، ایاب و ذهاب) — حتی اگر قبلاً تکمیل شده و فاکتور گرفته بوده — پرداختِ آنلاینِ آن فاکتور از این نسخه در **همهٔ** مسیرها بسته است: اپ مشتری، رسیدِ عمومی، صفحهٔ پرداخت و شروعِ تراکنش. سفارشِ «انجام کار» و سفارش‌های در جریان مثل قبل قابلِ پرداخت‌اند.

دو فیلدِ صریح اضافه شد تا اپ از روی وضعیتِ سفارش حدس نزند:

```json
"payment": {
  "payable": false,
  "payable_reason": "این سفارش بسته شده است و پرداخت آنلاین ندارد.",
  "pay_url": null,
  "direct_pay_url": null,
  "payment_url": null,
  "public_token": "…"
}
```

همین دو فیلد در `GET /crm/pay/{token}/status` هم آمده‌اند (`payable`, `payable_reason`).

**کار اپ:**
- دکمهٔ پرداخت را فقط وقتی نشان دهید که `payment.payable === true` باشد (به‌جای شرط‌های محلی روی وضعیت سفارش/مبلغ).
- وقتی `false` است، در صورت نیاز `payable_reason` را نمایش دهید — متن فارسیِ آمادهٔ نمایش است و برای همهٔ حالت‌ها پر می‌شود: پرداخت‌شده، لغو، جایگزین‌شده، نقدی، مبلغ صفر، سفارشِ بسته‌شده.
- `public_token` مثل قبل همیشه هست (برای poll کردن وضعیت).
