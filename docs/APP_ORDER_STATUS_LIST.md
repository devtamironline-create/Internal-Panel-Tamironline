# نامه به تیم اپلیکیشن مشتری — لیست کامل وضعیت‌های سفارش (به‌روزرسانی)

سیستمِ وضعیتِ سفارش در پنل گسترش یافته و **وضعیت‌های جدیدی** به چرخهٔ سفارش
اضافه شده‌اند که از این پس تکنسین/اپراتور می‌توانند ست کنند. این سند می‌گوید
اپ چه چیزی از API می‌گیرد و چه کاری لازم است.

## ✅ خبرِ مهم: نسخهٔ فعلیِ اپ نمی‌شکند
بک‌اند همهٔ وضعیت‌های جدید را به **همان رشته‌ها/عددهای قبلیِ شناخته‌شدهٔ اپ**
نگاشت می‌کند (backward-compatible). پس نسخهٔ production فعلی بدونِ هیچ تغییری
درست کار می‌کند. کارِ شما «بهبودِ نمایش» است، نه فیکسِ اضطراری.

## فیلدهای وضعیت در پاسخِ API
`GET /api/bff/v1/customer/orders/{id}` (و لیست):

| فیلد | توضیح |
|---|---|
| `status` | رشتهٔ وضعیت برای اپ — فقط از مجموعهٔ ثابتِ پایین |
| `status_int` | همان به‌صورت عددی |
| `status_label` | **برچسبِ دقیقِ فارسی** — همیشه درست‌ترین متن برای نمایش |
| `is_terminal` | آیا سفارش بسته شده (completed/cancelled/declined) |

> ⭐ توصیهٔ اصلی: در UI متنِ وضعیت را از **`status_label`** نمایش دهید (نه از
> نگاشتِ محلیِ `status`). این‌طوری وضعیت‌های جدید بدونِ هیچ آپدیتِ اپ، با متنِ
> دقیقِ فارسی دیده می‌شوند. از `status` فقط برای رنگ/آیکن/مرحلهٔ timeline
> استفاده کنید.

## جدولِ کاملِ وضعیت‌ها (بعد از این به‌روزرسانی)

| وضعیتِ داخلی پنل | برچسبِ فارسی (`status_label`) | `status` اپ | `status_int` | توضیح برای UX |
|---|---|---|---|---|
| new | جدید | `pending` | 0 | ثبت شده، هنوز هماهنگ نشده |
| awaiting_coordination ⭐ | در انتظار هماهنگی | `pending` | 0 | در صفِ تماس/هماهنگی |
| no_answer ⭐ | مشتری پاسخگو نیست | `pending` | 0 | تماس ناموفق — منتظرِ تماسِ بعدی |
| coordinated | هماهنگ شده | `assigned` | 1 | تکنسین و زمان مشخص شده |
| open | باز شده | `scheduled` | 2 | دستگاه به تعمیرگاه منتقل شده |
| repair_started ⭐ | شروع تعمیر | `in_progress` | 6 | تعمیر عملاً شروع شده |
| awaiting_part ⭐ | در انتظار قطعه | `suspended` | 3 | توقفِ موقت برای تأمینِ قطعه |
| awaiting_customer_approval ⭐ | در انتظار تأیید مشتری | `suspended` | 3 | منتظرِ تأییدِ مشتری (مثلاً هزینه) — بهترین جا برای CTA «پیش‌فاکتور را ببینید» |
| suspended | معلق | `suspended` | 3 | وضعیت نامشخص/معلق |
| transit | ایاب و ذهاب | `in_progress` | 6 | فقط هزینهٔ رفت‌وآمد |
| returned | برگشتی گارانتی | `in_progress` | 7 | سرویسِ مجددِ گارانتی |
| completed | انجام کار | `completed` | 5 | پایانِ موفق (terminal) |
| cancelled | کنسل شده | `cancelled` | 4 | لغو (terminal) |
| declined | رد شده | `declined` | 9 | ردِ تکنسین (terminal) |

⭐ = وضعیتِ جدید. توجه: چند وضعیتِ داخلی روی یک `status` اپ می‌افتند —
تفکیک‌شان فقط از `status_label` ممکن است.

## چک‌لیستِ اپ
- [ ] متنِ وضعیت در همهٔ صفحات از `status_label` خوانده شود.
- [ ] برای `suspended`، آیکن/رنگِ «در انتظار» استفاده شود (نه خطا) — چون حالا
      شاملِ «در انتظار قطعه» و «در انتظار تأیید مشتری» هم هست.
- [ ] (اختیاری - فاز بعد) اگر `status_label == «در انتظار تأیید مشتری»` و
      `proformas[]` غیرخالی است، CTA مشاهدهٔ پیش‌فاکتور برجسته شود.
- [ ] timeline سفارش (اگر دارید) با ۴ مرحلهٔ کلی بماند: ثبت → هماهنگی →
      در حال انجام → پایان؛ وضعیت‌های ریز فقط متنِ زیرِ مرحله شوند.

## پشتِ صحنه (سمتِ ما — انجام شد)
- تکنسین حالا در اپ/پنلِ خودش می‌تواند این وضعیت‌ها را ست کند: شروع تعمیر،
  در انتظار قطعه، در انتظار تأیید مشتری (علاوه بر قبلی‌ها).
- نگاشتِ backward-compatible در `OrderStatusMapper` انجام شد تا API مشتری برای
  وضعیت‌های جدید ۵۰۰ ندهد.
- پیامکِ خودکار برای وضعیت‌های جدید ارسال نمی‌شود (فقط هماهنگی/لغو/فاکتور مثل قبل).
