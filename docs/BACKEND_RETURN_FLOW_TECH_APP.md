# نامه به تیم توسعهٔ اپ تکنسین — فلوی جدید سفارش برگشتی

**تاریخ:** ۱۴۰۵/۰۵/۲۴ — **از:** تیم بک‌اند پنل — **موضوع:** بازطراحی فرایند «بررسی برگشتی» + قرارداد نهایی API

## چه چیزی عوض شد و چرا

تا امروز سؤال «آیا ایراد از خدمات قبلی است؟» بلافاصله بعد از برگشت‌خوردن سفارش جلوی تکنسین می‌آمد؛ در حالی که تکنسین هنوز نه با مشتری هماهنگ کرده و نه دستگاه را دیده است. از این نسخه، **تصمیم بررسی برگشتی به بعد از مراجعه در محل منتقل شده** و سرور آن را enforce می‌کند.

## فلوی کامل (سمت سرور قطعی است)

```
مشتری شکایت می‌کند
   ↓
اپراتور سفارش را «برگشتی گارانتی» می‌کند و کارشناسی اولیه انجام می‌دهد
   ↓ (تأیید اپراتور)
سفارش با وضعیت «هماهنگ شده» و return_review_pending=true به همان تکنسین
برمی‌گردد + پیامک/پوش «سفارش برگشت خورد» (event: tech_order_returned)
   ↓
تکنسین مثل یک سفارش عادی: نتیجهٔ تماس → تنظیم زمان مراجعه → مراجعه
   (بررسی برگشتی در این مرحله اجباری نیست — فقط بنر یادآور نمایش دهید)
   ↓ در محل، بعد از دیدن دستگاه
تکنسین «بررسی برگشتی» را ثبت می‌کند:
   ✅ تأیید = ایراد از کار قبلی → ادامهٔ رایگان (فقط «پایان سفارش» با مبلغ صفر)
   ❌ رد   = ایراد جدید → قیمت‌گذاری و فلوی عادی
   ↓
سرور اجازهٔ «بستن سفارش» (تکمیل/ایاب و ذهاب/…) را تا قبل از ثبت بررسی نمی‌دهد
```

دو خط قرمز سمت سرور:

1. **بررسی، هماهنگی را بلاک نمی‌کند.** تا وقتی `return_review_pending=true` است، همهٔ اکشن‌های فاز هماهنگی (نتیجهٔ تماس، زمان مراجعه، وضعیت‌های غیرنهایی مثل «شروع تعمیر») آزادند.
2. **بستن بدون بررسی ممکن نیست.** هر تلاش برای وضعیت نهایی (completed / transit / cancelled / declined) با **422** و این پیام رد می‌شود:
   > «این سفارش برگشتی است؛ قبل از بستن، ابتدا نتیجهٔ بررسی برگشتی (تأیید یا رد) را پس از مراجعه در محل ثبت کنید.»

## قرارداد API (برای اپ)

### ۱) تشخیص سفارش برگشتی — `GET /v1/technician/orders/{id}`

```json
{
  "return_review_pending": true,
  "return_review": {
    "pending": true,
    "reviewed_at": null,   // ISO8601 بعد از ثبت
    "approved": null,      // true/false بعد از ثبت
    "days": null           // فقط وقتی approved=true
  },
  "allowed_transitions": [ /* فقط گذارهای غیرنهایی تا وقتی pending=true */ ]
}
```

- تا وقتی `pending=true`: بنر «بررسی برگشتی — پس از مراجعه در محل» نشان دهید (متن‌ها در `app-messages`: کلیدهای `return_review_*` به‌روز شده‌اند). دکمهٔ ثبت بررسی از همان ابتدا فعال باشد — اما آن را اجباریِ لحظهٔ ورود نکنید.
- `allowed_transitions` را از سرور بخوانید و دکمه‌ها را از همین لیست بسازید؛ وضعیت‌های بستن تا قبل از ثبت بررسی اصلاً در لیست نمی‌آیند.

### ۲) ثبت نتیجهٔ بررسی — `POST /v1/technician/orders/{id}/return-review`

| فیلد | نوع | قاعده |
|---|---|---|
| `approved` | boolean | اجباری — `1` تأیید، `0` رد |
| `days` | int ۱..۱۴ | فقط وقتی `approved=1` اجباری — تخمین انجام کار |
| `note` | string ≤۱۰۰۰ | اختیاری |

- پاسخ موفق: `{success, message, data: {return_review_pending: false, approved, days, reviewed_at}}`
- **idempotent** است: اگر بعد از خطای شبکه دوباره POST کنید، همان نتیجهٔ قبلی با 200 برمی‌گردد و اثر دوباره ندارد.
- اگر سفارش در انتظار بررسی نباشد → 422 «این سفارش در انتظار بررسی برگشتی نیست.»

### ۳) بعد از ثبت بررسی

- **تأیید (`approved=1`):** سرور `return_type=1` می‌گذارد. `allowed_transitions` فقط «پایان سفارش» می‌شود. در بلاک تکمیل، عکس/توضیحات/مبلغ اجباری نیستند (تکمیل رایگان، مبلغ ۰).
- **رد (`approved=0`):** سفارش کاملاً عادی ادامه می‌یابد — همهٔ قواعد معمول تکمیل (عکس، توضیحات فاکتور، مبلغ > ۰) برقرارند.

### ۴) نکتهٔ مالی (سمت پنل — فقط برای اطلاع)

- در ادامهٔ رایگان (تأیید)، **فاکتور اصلیِ کار اول دست نمی‌خورد** و سند مالی معتبر می‌ماند.
- در مسیر رد، تکمیل جدید فاکتور جدید صادر می‌کند و فاکتور قبلی بایگانی می‌شود ولی لینک عمومی و صفحهٔ ادمینش همیشه باز می‌ماند (۴۰۴ نمی‌شود).

## اعلان‌ها (یادآوری مجدد)

- لحظهٔ ارجاع برگشتی: پیامک `tech_order_returned` + پوش `tech_order_returned` («{order_code} منتظر تأیید یا رد شماست.») ارسال می‌شود.
- SLA سفارش برگشتی همان SLA عادی است: «هماهنگ شده» بدون زمان مراجعه ۲۴ ساعت مهلت دارد؛ با ثبت زمان مراجعه، همان زمان مبنا می‌شود. یادآورهای `tech_sla_warning`/`tech_sla_due` طبق روال ارسال می‌شوند.
