# اپ + سایت — OTPِ ۴رقمی، تشخیصِ خودکارِ کد، و سیاستِ نشست (session)

سه تصمیمِ محصول که از سمتِ بک‌اند اعمال/پشتیبانی شده و فرانت/اپ باید هماهنگ شوند.

## ۱) OTP از ۶ رقم به ۴ رقم تغییر کرد

- بک‌اند از این به بعد کدِ **۴رقمی** تولید می‌کند (قابلِ برگشت با env: `SMS_OTP_LENGTH`).
- Endpointها و قرارداد هیچ تغییری نکرده‌اند — همان `POST /v1/auth/send-otp` و
  `POST /v1/auth/verify-otp`؛ اعتبارسنجیِ سرور از قبل ۴ تا ۸ رقم را می‌پذیرد.
- **کارِ فرانت/اپ:** تعدادِ خانه‌های ورودیِ کد از ۶ به **۴** برسد. اگر طول را
  هاردکد کرده‌اید (validation یا UI)، آن را از طولِ واقعیِ کدِ دریافتی یا یک
  ثابتِ ۴ بگیرید.
- انقضای کد و محدودیت‌ها همان قبلی است (۲ دقیقه اعتبار، ۶۰ ثانیه فاصله‌ی ارسال).

## ۲) تشخیصِ خودکارِ OTP (بدونِ تایپِ کاربر) — الزامی

کاربر نباید کد را دستی تایپ کند؛ سیستم باید پیامک را خودکار بخواند و در
فیلدها بگذارد.

### PWA (app.tamironline.com) و سایت — WebOTP API

1. **قالبِ پیامکِ کاوه‌نگار باید یک خطِ آخرِ استاندارد بگیرد.** فرمتِ فعلی:

   ```
   کد تایید شما : 971301
   Tamironline.com #971301
   لغو11
   ```

   خطِ `Tamironline.com #971301` برای WebOTP **معتبر نیست** — استاندارد این است
   که «آخرین خطِ» پیامک دقیقاً به این شکل باشد (با @ و دامنه‌ی صفحه‌ای که کد را
   می‌خواهد):

   ```
   کد تایید شما: 1234
   لغو11
   @app.tamironline.com #1234
   ```

   - برای فرمِ لاگینِ خودِ سایت، دامنه `@tamironline.com` است. اگر یک قالبِ
     مشترک می‌خواهید، خطِ آخر را دامنه‌ی اصلی بگذارید و خطِ ماقبلِ آخر را
     دامنه‌ی دوم: WebOTP اجازه‌ی چند origin در خطوطِ انتهایی را دارد
     (`@tamironline.com #1234` در یک خط و `@app.tamironline.com #1234` در خطِ بعد).
   - این تغییر در **پنلِ کاوه‌نگار** (متنِ قالبِ verify) انجام می‌شود؛ کد از
     placeholder همان `%token` است.

2. **کارِ فرانت:**

   ```html
   <input inputmode="numeric" autocomplete="one-time-code" pattern="[0-9]*" maxlength="4">
   ```

   ```js
   if ('OTPCredential' in window) {
     const ac = new AbortController();
     navigator.credentials.get({ otp: { transport: ['sms'] }, signal: ac.signal })
       .then(otp => { input.value = otp.code; form.submit(); })
       .catch(() => {});
   }
   ```

   - iOS/Safari از WebOTP پشتیبانی نمی‌کند ولی با `autocomplete="one-time-code"`
     کد را بالای کیبورد پیشنهاد می‌دهد — همین attribute برای iOS کافی است.

### اپِ نیتیوِ اندروید (در صورتِ وجود)

- **SMS User Consent API** ساده‌ترین راه است (نیازی به تغییرِ متنِ پیامک ندارد؛
  یک دیالوگِ سیستمیِ یک‌کلیکه به کاربر نشان می‌دهد).
- **SMS Retriever API** تجربه‌ی کاملاً بی‌صدا می‌دهد ولی متنِ پیامک باید hash
  یازده‌کاراکتریِ اپ را در انتها داشته باشد — اگر این مسیر را خواستید، hash اپ
  را اعلام کنید تا در قالبِ کاوه‌نگار اضافه شود.

## ۳) سیاستِ نشست — کاربر نباید زود به صفحه‌ی لاگین بیفتد

وضعیتِ بک‌اند (از قبل برقرار است):

- توکنِ sanctum **۳۰ روز** اعتبار دارد (`SANCTUM_TOKEN_EXPIRATION`).
- **Rolling token:** وقتی توکن واردِ نیمه‌ی دومِ عمرش شود (بعد از ~۱۵ روز)، هر
  پاسخِ موفقِ API یک هدرِ `X-Renewed-Token` با توکنِ تازه‌ی ۳۰روزه می‌دهد.

یعنی: کاربری که حداقل هر ۱۵–۳۰ روز یک‌بار اپ را باز کند، **هرگز نباید صفحه‌ی
لاگین را ببیند**. اگر کاربران زودتر لاگ‌اوت می‌شوند، مشکل سمتِ کلاینت است.

**کارِ اپ/فرانت (چک‌لیستِ الزامی):**

1. هدرِ `X-Renewed-Token` را در **هر** پاسخ چک کنید؛ اگر بود، توکنِ ذخیره‌شده را
   بلافاصله و اتمیک جایگزین کنید (توکنِ قدیمی تا انقضای واقعی‌اش معتبر می‌ماند،
   پس race خطرناک نیست — ولی ذخیره‌نکردنش یعنی لاگ‌اوت در روزِ ۳۰).
2. توکن را در storage پایدار نگه دارید (نه sessionStorage/حافظه) و **هنگامِ
   آپدیتِ اپ/سرویس‌ورکر پاکش نکنید** — پاک‌سازیِ cache نباید storage توکن را بزند.
3. فقط با **401 واقعی** کاربر را به لاگین بفرستید — نه با خطای شبکه/۵۰۰/timeout.
   الگوی درست: روی 401 یک‌بار retry با توکنِ ذخیره‌شده، اگر باز 401 بود → لاگین.
4. بعد از verify-otp موفق، توکنِ جدید را قبل از هر navigation ذخیره کنید.

اگر بعد از این چک‌لیست باز هم لاگ‌اوتِ زودهنگام دیدید، timestamp و پاسخِ دقیقِ
اولین 401 را بفرستید تا سمتِ سرور بررسی شود (لاگِ توکن‌ها نگه‌داری می‌شود).
