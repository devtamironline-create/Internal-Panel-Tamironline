## درخواست ۲ — فیلدهای SLA

روی **هر دو** ریسورس (`TechOrderListResource` و `TechOrderDetailResource`):

```json
{
  "assigned_at": "2026-07-29T10:02:11+00:00",
  "status_changed_at": "2026-07-29T10:02:11+00:00",
  "sla_deadline_at": "2026-07-29T11:02:11+00:00",
  "return_review_pending": false
}
```

`sla_deadline_at` را **سرور** محاسبه می‌کند (`Modules\CRM\Support\SlaPolicy`). مبنای زمانی برای هر وضعیت فرق دارد:

| وضعیت | مبنا | مهلت پیش‌فرض |
|---|---|---|
| جدید / در انتظار هماهنگی | `assigned_at` | ۱ ساعت |
| مشتری پاسخگو نیست | `assigned_at` | ۴۸ ساعت |
| هماهنگ شده | `visit_scheduled_at` | خودِ زمان مراجعه |
| انتقال به تعمیرگاه | `estimated_ready_at` → وگرنه `status_changed_at` | ۱۴ روز |
| معلق | `status_changed_at` | ۷۲ ساعت |
| در انتظار قطعه | `estimated_ready_at` → وگرنه `status_changed_at` | ۷ روز |
| در انتظار تأیید مشتری | `status_changed_at` | ۲۴ ساعت |
| شروع تعمیر | `status_changed_at` | ۵ روز |

**قرارداد `null`:** اگر مبنای زمانی روی سفارش نباشد (مثلاً `assigned_at` خالی)، `sla_deadline_at` برابر `null` می‌آید. معنی‌اش **«قابل محاسبه نیست»** است، نه «گذشته». اپ نباید برای آن یادآور بسازد و نباید قفل کند.

روی جزئیات، این‌ها هم می‌آیند: `estimated_ready_at` (تخمین خود تکنسین) و `max_estimate_date` (سقفی که تکنسین می‌تواند انتخاب کند).

اعداد ساعت‌ها از پنل ادمین قابل تغییرند و از `GET /app-config` هم برمی‌گردند.

## درخواست ۳ — `GET /v1/technician/me/sync`

```
GET /v1/technician/me/sync
Authorization: Bearer <token>
```

```json
{
  "success": true,
  "data": {
    "server_time": "2026-07-29T10:15:00+00:00",
    "orders": {
      "actionable_count": 4,
      "latest_assigned_at": "2026-07-29T10:02:11+00:00",
      "latest_order": {
        "id": 8842,
        "order_code": "TO-8842",
        "customer_name": "…",
        "device_name": "…"
      }
    },
    "messages":      { "unread": 2 },
    "announcements": { "unread": 1 },
    "next_deadline_at": "2026-07-29T11:00:00+00:00"
  }
}
```

**تعریف دقیق فیلدها:**

- `actionable_count` — سفارش‌هایی که هنوز تصمیم تکنسین را می‌خواهند. وضعیت‌های نهایی و `declined` کنار می‌روند. **استثنا:** `transit` شمرده می‌شود، چون با اینکه `is_final` آن `true` است، هنوز مهلت دارد و منتظر تصمیم است.
- `latest_assigned_at` / `latest_order` — بر اساس `assigned_at`، نه `created_at`. سفارشی که قبلاً دیده شده ولی دوباره تخصیص یافته، اینجا «جدید» به حساب می‌آید.
- `next_deadline_at` — نزدیک‌ترین سررسیدِ **آینده**. مهلت‌های گذشته نادیده گرفته می‌شوند (`null` اگر هیچ سررسید آینده‌ای نباشد).
- `unread` پیام‌ها فقط پیام‌های **اپراتور** را می‌شمارد، نه پیام‌های خود تکنسین.

پاسخ زیر `no-cache` می‌رود و هیچ رابطهٔ سنگینی لود نمی‌کند.

## درخواست ۱ — پیامک رویدادهای فوری

### قالب‌های موجود

| trigger_key | رویداد | اولویت | نام الگوی کاوه‌نگار |
|---|---|---|---|
| `order_assigned_tech` | تخصیص سفارش جدید | 🔴 | (از قبل موجود) |
| `tech_sla_warning` | یک ساعت مانده به مهلت | 🟠 | `techslawarning` |
| `tech_sla_due` | رسیدن مهلت | 🔴 | `techsladue` |
| `tech_order_returned` | برگشت خوردن سفارش | 🟠 | `techorderreturned` |

> **اقدام لازم از سمت شما/مدیر:** سه الگوی بالا باید در پنل کاوه‌نگار ثبت و تأیید شوند. تا آن زمان قالب‌ها **غیرفعال** مانده‌اند — فعال‌کردنشان فقط خطای ارسال تولید می‌کند. بعد از تأیید، از `/crm/sms-management` فعال می‌شوند.

متن‌های پیشنهادی (سه توکن: نام تکنسین، کد سفارش، خالی):

```
{technician_name} عزیز
یک ساعت تا پایان مهلت ثبت وضعیت سفارش {order_code} باقی است.
لطفاً در اپ تعمیرآنلاین وضعیت را ثبت کنید.
```

```
{technician_name} عزیز
مهلت ثبت وضعیت سفارش {order_code} رسید.
تا ثبت نشدن وضعیت، امکان ادامهٔ کار در اپ نیست.
```

```
{technician_name} عزیز
سفارش {order_code} برگشت خورده و منتظر تأیید یا رد شماست.
لطفاً در اپ تعمیرآنلاین بررسی کنید.
```

### ضدِتکرار

هر (سفارش، رویداد، شمارهٔ تکنسین) فقط **یک‌بار** پیامک می‌گیرد. مرجع، خودِ جدول `crm_sms_logs` است.

برای دو رویدادی که قانوناً می‌توانند تکرار شوند، «اثر انگشت» دقیق‌تر است:

- **تخصیص** — اثر انگشت `assign:<timestamp of assigned_at>`. تخصیص مجدد رویداد تازه‌ای است و پیامک می‌گیرد؛ اجرای دوبارهٔ همان تخصیص نه.
- **مهلت** — اثر انگشت `sla:<status>:<deadline timestamp>`. تا وقتی تکنسین وضعیت را عوض نکرده، هرچند بار هم که زمان‌بند اجرا شود پیامک دوباره نمی‌رود؛ به‌محض تغییر وضعیت، مهلت تازه یادآور تازه دارد.

### ساعت مجاز ارسال

قابل تنظیم در `/crm/sms-management` (پیش‌فرض ۸ صبح تا ۱۰ شب). دو عدد برابر یعنی «بدون محدودیت».

**فقط** روی اعلان‌های اپ تکنسین اعمال می‌شود. دو رویداد 🔴 — تخصیص سفارش جدید و رسیدن مهلت — مستثنا هستند و هر ساعتی می‌روند، چون نگه‌داشتنشان تا صبح خود پیام را بی‌اثر می‌کند. سایر پیامک‌ها (مشتری، کیف‌پول، فاکتور) دست‌نخورده‌اند.

### کلید فعال/غیرفعال

هر قالب کلید مستقل خودش را در `/crm/sms-management` دارد.

### زمان‌بندی

```
crm:orders:sla-reminders   هر ۱۵ دقیقه
```

پنجرهٔ تحمل ۲۰ دقیقه است تا یک اجرای ازدست‌رفته (ری‌استارت سرور، کندی صف) سررسید را برای همیشه نسوزاند. اگر یک اجرا از دست برود و حالا مهلت هم گذشته باشد، پیامک «یک ساعت مانده» **ارسال نمی‌شود** — سررسید بر یادآور مقدم است، چون آن متن دیگر درست نیست.

## درخواست ۵ — زیرساخت پوش

```
POST   /v1/technician/me/push-token
DELETE /v1/technician/me/push-token
```

```json
// POST body
{
  "token": "ExponentPushToken[…]",
  "provider": "expo",        // expo | pushe | chabok — اختیاری، پیش‌فرض expo
  "platform": "android",     // ios | android — اختیاری
  "device_name": "Pixel 7",  // اختیاری
  "app_version": "1.4.2"     // اختیاری
}

// پاسخ
{ "success": true, "data": { "registered": true, "push_enabled": false } }
```

`push_enabled: false` یعنی سرویس پوش هنوز انتخاب نشده و **هیچ نوتیفیکیشنی ارسال نمی‌شود**. اپ نباید انتظار پوش داشته باشد تا این پرچم `true` شود.

چرا الان ساخته شد: اگر پایگاه توکن از امروز پر شود، روزی که سرویس داخلی انتخاب شد فقط کار سمت سرور می‌ماند و منتظر انتشار نسخهٔ جدید اپ نمی‌مانیم.

یکتایی روی خودِ توکن است، نه (تکنسین، دستگاه): گوشی‌ای که بین دو حساب دست‌به‌دست شود، ردیفش به تکنسین جدید منتقل می‌شود و دو ردیف زندهٔ همزمان نمی‌سازد. `DELETE` هنگام خروج از حساب صدا زده شود.

قرارداد payload که در نامه آمده بود (`type` / `order_id` / `ticket_id`) و کانال‌های اندروید بدون تغییر پذیرفته می‌شود؛ در روز فعال‌سازی همان را می‌فرستیم.

## آنچه هنوز باقی است

- **اعلامیهٔ فوری ادمین (🟡)** — پیاده نشد. سه رویداد دیگر به سفارش گره خورده‌اند و از `crm_sms_logs.order_id` ضدِتکرار می‌گیرند؛ اعلامیه سفارش ندارد و به مدل ارسال گروهی جدا نیاز دارد. اگر اولویت دارد، جداگانه اعلام کنید.
- **`POST /orders/{id}/return-review`** — در این نامه نبود. فیلد `return_review_pending` و پیامکش آماده است؛ خودِ اندپوینتِ تأیید/رد هنوز ساخته نشده.
- **ارسال واقعی پوش** — منتظر انتخاب سرویس (Pushe/چابک) و ثبت‌نام.
