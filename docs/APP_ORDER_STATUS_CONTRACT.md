# پاسخِ بک‌اند — قراردادِ «وضعیتِ سفارش» و «تعمیرکار»

**به:** تیم اپ مشتری — **موضوع:** رفعِ تناقضِ وضعیت ↔ مرحله ↔ تعمیرکار

## جمع‌بندی
تناقضِ مشاهده‌شده (بجِ «جدید» + مرحلهٔ «تکنسین تعیین شد» خاکستری + نمایشِ تعمیرکار)
از این می‌آمد که سفارش در فازِ «ثبت‌شده» بود ولی داخلی یک تکنسین بهش تخصیص خورده و
اپ صرفِ وجودِ object تعمیرکار را نشان می‌داد. **سمتِ بک‌اند اصلاح شد:** حالا فیلدِ
`technician` فقط وقتی در payload می‌آید که سفارش رسماً از فازِ `pending` عبور کرده
باشد. پس این تناقض برای همهٔ نسخه‌های اپ برطرف است.

---

## ۱) مقادیرِ رسمیِ `status`
اپ همیشه یکی از **همین ۸ مقدارِ نگاشت‌شده** را می‌گیرد (نه enumِ داخلیِ پنل):

```
pending · assigned · scheduled · in_progress · suspended · completed · cancelled · declined
```

enumِ داخلیِ پنل ریزتر است و در بک‌اند به این ۸ تا **fold** می‌شود:

| داخلی (پنل) | `status` (اپ) | `status_int` |
|---|---|---|
| new | pending | 0 |
| awaiting_coordination | pending | 0 |
| no_answer | pending | 0 |
| coordinated | assigned | 1 |
| open | scheduled | 2 |
| awaiting_part | suspended | 3 |
| awaiting_customer_approval | suspended | 3 |
| suspended | suspended | 3 |
| transit | in_progress | 6 |
| returned | in_progress | 7 |
| completed | completed | 5 |
| cancelled | cancelled | 4 |
| declined | declined | 9 |

**`new` جداگانه به اپ نمی‌رسد** — به `pending` نگاشت می‌شود. حق با شماست که «جدید»
را جدا نمی‌شناسید.

## ۲) `status` منبعِ حقیقتِ منطق است، `status_label` فقط نمایش
- برای **منطق** (stepper، گیتِ لغو، نمایشِ تعمیرکار) از `status`/`status_int`
  استفاده کنید.
- `status_label` یک **برچسبِ فارسیِ ریزتر و فقط‌نمایشی** است (مثلِ «هماهنگ شده»،
  «در انتظار قطعه»، «باز شده») که همان بجِ وضعیت را پر می‌کند. همیشه با `status`
  هم‌ریشه است ولی دقیق‌تر (چند وضعیتِ داخلی به یک `status` می‌افتند ولی برچسبِ
  متفاوت دارند). **منطق را از `status_label` استخراج نکنید.**

## ۳) `technician` کِی می‌آید؟
- یک **تخصیصِ واقعی** است (نه placeholder). «تکنسین آموزشی» یک حسابِ واقعیِ
  تستی/آموزشی بوده که داخلی اختصاص یافته بود.
- **از این پس:** `technician` فقط وقتی در payload هست که `status != pending`
  باشد؛ سفارشِ pending دیگر تعمیرکار نشان نمی‌دهد. پس تناقضِ stepper ↔ تعمیرکار
  حذف شد.
- فیلدِ `technician_assigned_at` هم اضافه شد (زمانِ داخلیِ تخصیص) — صرفاً برای
  اطلاع؛ ملاکِ نمایش، خودِ `status` است (چون تخصیصِ داخلی ممکن است در فازِ
  `pending` هم رخ دهد).

## ۴) منبعِ «مرحله»
فیلدِ جدا برای درصدِ پیشرفت نداریم؛ stepper را از `status` بسازید. توجه:
- **`status_int` رتبه/ترتیبِ پیشرفت نیست** (مثلاً in_progress=6 ولی completed=5) —
  فقط شناسه است. برای stepper از ترتیبِ ثابتِ زیر استفاده کنید:
  `pending → assigned → scheduled → in_progress → completed`.
- **`suspended`** (شاملِ awaiting_part / awaiting_customer_approval): یک حالتِ
  «مکث» است، نه یک مرحلهٔ روبه‌جلو — روی مرحلهٔ فعلی به‌صورتِ بجِ «معلق» نشان دهید،
  نه یک step جدا.
- **`cancelled` / `declined`**: پایانی‌اند (`is_terminal=true`) — به‌صورتِ حالتِ
  پایانی نمایش دهید، نه روی خطِ stepper.

## ۵) کاملیِ enum
فهرستِ ۸‌تاییِ شما **کامل** است. هر زیروضعیتِ جدیدِ پنل هم در بک‌اند به یکی از همین
۸ مقدار fold می‌شود (فقط `status_label`ش فرق می‌کند)، پس هرگز `status`ی خارج از
این ۸ تا به اپ نمی‌رسد و اپِ production کرش نمی‌کند.

---

خلاصه: `status`/`status_int` = منطق · `status_label` = نمایش · `is_terminal` = گیتِ
پایان · `technician` فقط بعد از عبور از `pending` (به‌علاوهٔ `technician_assigned_at`
برای اطلاع). با این‌ها هیچ تناقضِ وضعیت↔مرحله↔تعمیرکار نباید بماند.
