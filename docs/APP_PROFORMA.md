# اپ — پیش‌فاکتور (Proforma / برآوردِ قیمت)

پیش‌فاکتور یک «برآوردِ قیمتِ قبل از انجامِ کار» است که تکنسین (از اپ/پنلِ تکنسین)
یا اپراتور (از پنلِ ادمین) صادر می‌کند و برای مشتری با پیامک ارسال می‌شود.
مشتری آن را می‌بیند و تصمیم می‌گیرد. **این سند برای تیمِ توسعهٔ اپلیکیشن است**
تا صفحهٔ نمایشِ پیش‌فاکتور را در اپِ مشتری بسازد.

> پیش‌فاکتور با «فاکتور» فرق دارد: فاکتور بعد از تکمیلِ کار و قطعیِ حساب صادر
> می‌شود (`/invoice/...`)؛ پیش‌فاکتور صرفاً یک پیشنهادِ قیمت است.

## جریانِ کار (سمتِ سرور — انجام‌شده)

1. تکنسین/ادمین اقلام (شرح، تعداد، قیمتِ واحد) + تخفیف را وارد می‌کند.
2. سرور یک پیش‌فاکتور با کدِ `PF-YYMM-NNNNN` و یک `public_token` ۴۰کاراکتریِ
   غیرقابل‌حدس می‌سازد.
3. با زدنِ «ارسال پیامک»، لینکِ عمومی به موبایلِ مشتری می‌رود (تمپلیتِ کاوه‌نگارِ
   `customer_proforma_issued`).

## نقشِ اپ

### ★ نمایش داخلِ جزئیاتِ سفارش (مهم — پیش‌فرض)

پیش‌فاکتورهای هر سفارش حالا **مستقیماً در پاسخِ جزئیاتِ سفارش** می‌آیند تا
مشتری آن‌ها را در همان صفحهٔ سفارش ببیند (بدونِ نیاز به لینکِ پیامک):

```
GET /api/bff/v1/customer/orders/{id}
```

پاسخ، کلیدِ `data.proformas` (آرایه) دارد — فقط پیش‌فاکتورهای **ارسال‌شده**
(پیش‌نویس‌ها پنهان‌اند). هر عنصر همان شکلِ زیر را دارد:

```jsonc
{
  "data": {
    "id": 77322,
    "tracking_code": "ORD-2607-01933",
    "status": "in_progress",
    // ... بقیهٔ فیلدهای سفارش ...
    "proformas": [
      {
        "id": 12,
        "code": "PF-2607-00003",
        "token": "aZ09...40char",
        "status": "sent",                 // draft هرگز این‌جا نمی‌آید
        "status_label": "ارسال‌شده",
        "customer_name": "رضا مشتری",
        "device_name": "لباسشویی",
        "brand_name": "سامسونگ",
        "items": [
          { "title": "تعویض برد اصلی", "quantity": 1, "unit_price": 800000, "total": 800000 }
        ],
        "subtotal": 1100000,
        "discount": 100000,
        "total": 1000000,                 // تومان (integer)
        "description": "برآورد اولیه",
        "valid_until": "2026-07-20",
        "order_id": 77322,
        "order_code": "ORD-2607-01933",
        "public_url": "https://app.tamironline.com/proforma/aZ09...",
        "created_at": "2026-07-09T11:54:28+00:00"
      }
    ]
  }
}
```

- آرایه‌ی خالی `[]` یعنی این سفارش پیش‌فاکتورِ ارسال‌شده ندارد → چیزی نشان ندهید.
- در صفحهٔ سفارش یک بخشِ «پیش‌فاکتور/برآوردِ قیمت» بگذارید و همین اقلام/مبلغ را
  رندر کنید (نیازی به فراخوانیِ جداگانه نیست). برای بازکردنِ رسیدِ کامل می‌توانید
  `public_url` را در WebView باز کنید یا با `token` به endpointِ زیر بروید.

### الف) سریع — WebView (از لینکِ پیامک)

لینکِ داخلِ پیامک (`receipt_url`) مستقیم یک صفحهٔ رسیدِ آمادهٔ موبایل است؛
کافی است در WebView باز شود. نیازی به کارِ اضافه نیست.

### ب) نیتیو — API عمومیِ token-based (توصیه‌شده)

```
GET /api/bff/v1/customer/proforma/{token}
```

- **بدونِ auth.** خودِ `token` (۴۰ کاراکتر، غیرقابل‌حدس) نقشِ احراز را دارد —
  دقیقاً مثلِ رسیدِ فاکتور. Header: `Cache-Control: private, no-store`.
- `{token}` را از انتهای لینکِ پیامک (بعد از آخرین `/`) یا از deep-link بردارید.

**پاسخِ موفق (200):**

```jsonc
{
  "success": true,
  "data": {
    "id": 12,
    "code": "PF-2607-00003",
    "token": "aZ09...40char",
    "status": "sent",                     // draft|sent|accepted|rejected|expired|converted
    "status_label": "ارسال‌شده",
    "customer_name": "رضا مشتری",
    "customer_mobile": "09121112233",
    "device_name": "لباسشویی",
    "brand_name": "سامسونگ",
    "items": [
      { "title": "تعویض برد اصلی", "quantity": 1, "unit_price": 800000, "total": 800000 },
      { "title": "دستمزد نصب",      "quantity": 2, "unit_price": 150000, "total": 300000 }
    ],
    "subtotal": 1100000,
    "discount": 100000,
    "total": 1000000,                     // مبلغِ نهایی به تومان
    "description": "برآورد اولیه",
    "valid_until": "2026-07-20",          // یا null
    "order_id": 77322,                    // یا null (پیش‌فاکتورِ مستقل)
    "order_code": "ORD-2607-01933",       // یا null
    "public_url": "https://app.tamironline.com/proforma/aZ09...",
    "created_at": "2026-07-09T11:54:28+00:00"
  }
}
```

**پاسخِ ناموجود (404):** `{ "success": false, "error": { "code": "not_found", "message": "..." } }`

## نکاتِ UI

- تیترِ صفحه: «پیش‌فاکتور {code}» + یک برچسبِ وضعیت (`status_label`).
- جدولِ اقلام: `title` / `quantity` / `unit_price` / `total` (اعداد را با جداکنندهٔ
  هزارگان و «تومان» نشان دهید).
- خلاصه: `subtotal` → `discount` (منفی) → **`total`** برجسته.
- اگر `valid_until` پر است، «معتبر تا …» را نمایش دهید؛ اگر گذشته، وضعیت را
  «منقضی» تلقی کنید (سرور هم `status` را نگه می‌دارد).
- **توضیحِ مهم برای کاربر:** این «پیش‌فاکتور/برآوردِ قیمت» است، نه فاکتورِ نهایی.
- `total` همیشه به **تومان** و integer است (نه ریال، نه اعشار).

## ارسالِ خودکارِ پیامک (مهم)

با **ساختِ** پیش‌فاکتور (چه در پنلِ ادمین، چه در اپ/پنلِ تکنسین)، پیامک
**به‌صورتِ خودکار** برای مشتری ارسال می‌شود و وضعیت به «ارسال‌شده» می‌رود؛
نیازی به زدنِ دکمهٔ جدا نیست. اگر ارسالِ خودکار ناموفق بود (مثلاً قالب فعال
نیست)، پیش‌فاکتور ساخته‌شده باقی می‌ماند و از دکمهٔ **«ارسال پیامک»** می‌توان
دوباره تلاش کرد. متنِ پیامک:

```
پیش فاکتور تعمیرآنلاین
{نام مشتری} عزیز، پیش فاکتور شما در لینک زیر قابل مشاهده است:
app.tamironline.com/proforma/{کدِ امن}
تعمیرآنلاین
```

لینک به دامنهٔ **اپ** اشاره می‌کند؛ اپ باید مسیرِ
`app.tamironline.com/proforma/{token}` را به‌عنوانِ deep-link/universal-link
بگیرد و همان صفحهٔ پیش‌فاکتور (با API یا WebView) را باز کند.

## نهایی کردن (تبدیل به فاکتور نهایی)

جریانِ کاملِ تکنسین در اپ/پنلِ تکنسین:

1. پیش‌فاکتور را می‌سازد → **خودکار برای مشتری پیامک می‌رود** و وضعیت «ارسال‌شده»
   می‌شود (در صورتِ نیاز، «ارسال پیامک» برای ارسالِ مجدد هست).
2. پس از توافقِ مشتری، در صفحهٔ پیش‌فاکتور دکمهٔ **«نهایی کردن (تکمیل سفارش)»**
   را می‌زند (فقط برای پیش‌فاکتورِ متصل به سفارش). این کار:
   - پیش‌فاکتور را **«تأیید مشتری»** علامت می‌زند،
   - تکنسین را به صفحهٔ **تکمیلِ همان سفارش** می‌برد، با **مبلغِ پیش‌فاکتور
     پیش‌پرشده** روی فیلدِ قیمتِ مشتری.
3. تکنسین وضعیت را «پایان سفارش» می‌گذارد و ثبت می‌کند → **فاکتورِ نهایی** از
   مسیرِ استاندارد (کمیسیون/کیف‌پول) صادر می‌شود و پیش‌فاکتور خودکار
   **«تبدیل‌شده»** (`status=converted`, `invoice_id` پر) می‌شود.

یعنی پیش‌فاکتور «برآورد» است و فاکتورِ نهایی همان فاکتورِ تکمیلِ سفارش؛ منطقِ
مالی یک مسیر بیشتر ندارد (بدونِ دوباره‌کاری/دوباره‌حساب).

اپِ مشتری فقط نمایش‌دهنده است؛ برای نمایشِ وضعیتِ نهایی، `status` را از API
بخوانید: `converted` یعنی فاکتورِ نهایی صادر شده (می‌توانید کاربر را به رسیدِ
فاکتور هدایت کنید).

## تأیید/رد توسطِ مشتری (فاز بعدی — اختیاری)

در این نسخه، پاسخِ مشتری (accept/reject) از طریقِ اپ هنوز endpoint ندارد و
هماهنگی تلفنی/حضوری انجام می‌شود. اگر اپ می‌خواهد دکمهٔ «تأیید/رد» بگذارد،
اعلام کنید تا `POST /v1/customer/proforma/{token}/respond` اضافه شود
(نیازمندِ تصمیمِ محصول دربارهٔ احرازِ مشتری برای این اکشن).

## سمتِ پنل (اطلاع)

- **ادمین:** منوی «مالی ← پیش‌فاکتورها» — ساخت با اقلامِ داینامیک، ارسالِ پیامک،
  مشاهدهٔ رسید. می‌تواند از یک سفارش پیش‌پر شود (`?order_id=`).
- **تکنسین (پنل/اپِ تکنسین):** داشبورد ← «پیش‌فاکتور» — فقط برای سفارش‌های
  خودش می‌سازد و فقط پیش‌فاکتورهای خودش را می‌بیند.

## راه‌اندازی روی سرور (یک‌بار)

1. migration اجرا شود (جدولِ `crm_proformas` + متنِ تمپلیتِ SMS + تنظیمِ لینکِ اپ).
2. **در کاوه‌نگار** یک تمپلیتِ تأییدشده با همین متن بسازید (تأییدِ کاوه‌نگار لازم
   است چون لینک دارد):
   ```
   پیش فاکتور تعمیرآنلاین
   %token عزیز، پیش فاکتور شما در لینک زیر قابل مشاهده است:
   app.tamironline.com/proforma/%token2
   تعمیرآنلاین
   ```
   یعنی `%token` = نامِ مشتری، `%token2` = کدِ امن (`{public_token}` — بدونِ
   کاراکترِ خاص تا کاوه‌نگار بپذیرد؛ دامنه داخلِ خودِ تمپلیت است).
3. در **پنل ← مدیریت پیامک ← قالبِ «صدور پیش‌فاکتور»**، فیلدِ
   `kavenegar_template` را برابرِ **نامِ همان تمپلیتِ تأییدشده** بگذارید و قالب را
   **فعال** کنید. مَپِ توکن‌ها را migration ست کرده:
   `token={customer_name}`، `token2={public_token}`، `token3={amount}`.
4. تنظیمِ `proforma_public_url_template` به‌صورتِ خودکار روی
   `https://app.tamironline.com/proforma/{token}` ست می‌شود (اگر قبلاً نبود) تا
   `public_url` در APIِ اپ به اپ اشاره کند — بدونِ نیاز به دیپلوی قابلِ تغییر.
