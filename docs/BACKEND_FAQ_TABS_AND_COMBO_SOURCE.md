# نامه به تیم فرانت — (۱) FAQ به‌صورت تب دسته‌بندی، (۲) منبعِ یگانه‌ی صفحات ترکیبی

> نسخه: 1.0 | هر دو تغییر backward-compatible هستند (فیلدِ قبلی حذف نشده).

---

## ۱) FAQ — نمایش به‌صورت تب (categories)

سکشن `faq` در **سه** endpoint زیر حالا علاوه بر `items` (لیست مسطح، مثل قبل)، یک آرایه‌ی جدید **`categories`** دارد تا هر دسته‌بندی را به‌صورت **تب** نشان دهید:

- `GET /v1/catalog/devices/{slug}` (صفحه‌ی دستگاه)
- `GET /v1/catalog/brands/{slug}` (صفحه‌ی برند)
- `GET /v1/catalog/devices/{deviceSlug}/{brandSlug}` (صفحه‌ی ترکیبی)

### شکل جدید پاسخ

```json
"faq": {
  "enabled": true,
  "items": [
    { "id": 12, "question": "…", "answer": "…" },
    { "id": 18, "question": "…", "answer": "…" }
  ],
  "categories": [
    {
      "id": 4,
      "name": "پشتیبانی",
      "slug": "support",
      "items": [ { "id": 12, "question": "…", "answer": "…" } ]
    },
    {
      "id": 7,
      "name": "گارانتی",
      "slug": "warranty",
      "items": [ { "id": 18, "question": "…", "answer": "…" } ]
    },
    {
      "id": null,
      "name": "عمومی",
      "slug": "general",
      "items": [ { "id": 30, "question": "…", "answer": "…" } ]
    }
  ]
}
```

| فیلد | توضیح |
|------|-------|
| `items` | **همه‌ی** سوالات به‌صورت مسطح و یکتا (مثل قبل) — برای سازگاری یا نمایشِ بدونِ تب. |
| `categories[]` | هر عضو یک **تب**: `{id, name, slug, items[]}`. |
| `categories[].id` | id دسته‌بندی (taxonomy). برای تبِ «عمومی» مقدار `null` است. |
| `categories[].name` | عنوانِ تب (مثلاً «پشتیبانی»). |
| `categories[].items` | سوالات همان دسته. |

### رفتار پیشنهادی در فرانت
- اگر `categories.length > 1` → **تب‌بندی** کن (هر `category.name` یک تب، محتوای آن `category.items`).
- اگر `categories.length <= 1` → همان نمایشِ ساده (آکوردین) با `items` کافی است.
- سوالاتِ منفرد/قدیمی (بدونِ دسته‌بندی) در تبِ **«عمومی»** (`slug: "general"`, `id: null`) جمع می‌شوند.
- منبعِ سوالاتِ هر تب همان `category.items` است؛ لازم نیست از `items` فیلتر کنی.

## ۲) صفحات ترکیبی (device × brand) — منبعِ یگانه شد

از این پس **«صفحه‌ی ترکیبیِ فعال» (در پنل: مدیریت صفحات ترکیبی / combo-manager) تنها منبعِ حقیقت** برای رابطه‌ی دستگاه↔برند است. سه اثر:

### الف) رفع ۴۰۴ صفحه‌ی ترکیبی
`GET /v1/catalog/devices/{device}/{brand}`:
- اگر صفحه‌ی ترکیبی **فعال** باشد → ۲۰۰ (دیگر به pivotِ دستی وابسته نیست). این همان باگ بود: `/services/refrigerator-freezer/aeg` با وجودِ فعال‌بودن، ۴۰۴ می‌داد.
- اگر صفحه‌ی ترکیبی **غیرفعال** باشد → **۴۰۴** (قبلاً ممکن بود همچنان رندر شود). یعنی غیرفعال‌کردن در پنل، صفحه را واقعاً مخفی می‌کند.

### ب) صفحه‌ی دستگاه — `sections.brands.items`
حالا فقط برندهایی برمی‌گردند که **comboشان فعال** است (`combo_active: true`). یعنی لیستِ برندهای صفحه‌ی دستگاه دقیقاً با combo-manager هم‌خوان است.

### ج) صفحه‌ی برند — `sections.devices.items`
متقارن: فقط دستگاه‌هایی که **comboشان فعال** است.

> نکته: `combo_href` و `combo_active` (که قبلاً اضافه شده بودند) سرِ جای‌شان هستند. حالا چون منبع یکی شده، عملاً همه‌ی آیتم‌های برگشتی `combo_active: true` خواهند بود (مگر در حالتِ legacyِ دستگاه/برندی که هنوز هیچ صفحه‌ی ترکیبی‌ای برایش ثبت نشده — که آنجا رفتارِ قدیمی حفظ شده).

### کار لازم در فرانت
- معمولاً **هیچ تغییری لازم نیست**؛ فقط بدانید که لیست برند/دستگاهِ این صفحات اکنون منبعِ واحد دارد و با پنل هم‌خوان است.
- مطمئن شوید لینکِ کارت‌های برند/دستگاه به `combo_href` (`/services/{device}/{brand}`) می‌رود.

## نکات عمومی
- هیچ فیلدِ قبلی حذف نشده؛ فقط `faq.categories` **اضافه** شده و رفتارِ ۴۰۴/لیست‌ها اصلاح شده.
- کشِ صفحات با ویرایش در پنل purge می‌شود (مسیر + تگ)؛ مطمئن شوید `revalidate_*` تنظیم است.
- میزبانِ تصاویر `panel.tamironline.com` است.
