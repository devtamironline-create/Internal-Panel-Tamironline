# نامه به تیمِ فرانت — همگام‌سازی و تستِ `INTERNAL_API_TOKEN` با بک‌اند

## چرا این نامه؟

در buildِ اخیرِ فرانت، fetchهای ISR به `/v1/catalog/devices/{slug}` با **401** شکستند.
بک‌اند این را با «IPِ معتمدِ سرورِ فرانت» حل کرد (بیلد از IPِ `62.220.124.156` دیگر
توکن نمی‌خواهد)، اما **توکنِ داخلی همچنان مهم است** و در runtime باید درست ارسال شود.
این نامه می‌گوید توکن کجاست، چطور بفرستید، و چطور **بدونِ افشای توکن** تست کنیم که
دو طرف یک مقدار را دارند.

---

## ۱) توکن کجا تعریف می‌شود؟

| طرف | محل |
|---|---|
| بک‌اند (پنل) | `.env` → `INTERNAL_API_TOKEN` (و در زمانِ چرخش: `INTERNAL_API_TOKEN_OLD`) |
| فرانت (BFF) | env سمتِ سرورِ Next (مثلاً `INTERNAL_API_TOKEN`) — **هرگز** با پیشوندِ `NEXT_PUBLIC_` |

## ۲) بک‌اند توکن را چگونه می‌پذیرد؟

هر دو شکل معتبر است (هر کدام راحت‌تر است):

```
Authorization: Bearer <token>
```
یا
```
X-Internal-Token: <token>
```

## ۳) تستِ تطابقِ توکن — بدونِ ردوبدلِ خودِ توکن 🔐

توکن را هرگز در چت/تیکت نفرستید. به‌جای آن **اثرانگشتِ SHA-256** را مقایسه کنید:

**بک‌اند (روی سرورِ پنل):**
```bash
php artisan tinker --execute='echo substr(hash("sha256", (string) config("services.internal.token")), 0, 12), PHP_EOL;'
```

**فرانت (روی سرورِ فرانت):**
```bash
node -e 'console.log(require("crypto").createHash("sha256").update(process.env.INTERNAL_API_TOKEN ?? "").digest("hex").slice(0,12))'
```

دو خروجی باید **دقیقاً یکی** باشند (۱۲ کاراکترِ اولِ هش). اگر فرق داشت، env یکی از
دو طرف قدیمی/اشتباه است. (خروجیِ هش را می‌توانید آزادانه در چت بفرستید — از آن
نمی‌شود توکن را برگرداند.)

## ۴) تستِ کاربردی (end-to-end) با curl

> نکته: از **سرورِ فرانت** تست نکنید — آن IP معتمد است و حتی بدونِ توکن هم 200
> می‌گیرد و نتیجه گمراه‌کننده می‌شود. از لپ‌تاپ/ماشینِ دیگری تست کنید:

```bash
# بدونِ توکن → باید 401 بدهد
curl -s -o /dev/null -w "%{http_code}\n" \
  https://panel.tamironline.com/v1/catalog/devices/gas-stove

# با توکنِ درست → باید 200 بدهد
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $INTERNAL_API_TOKEN" \
  https://panel.tamironline.com/v1/catalog/devices/gas-stove

# با توکنِ غلط → باید 401 بدهد
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer wrong-token" \
  https://panel.tamironline.com/v1/catalog/devices/gas-stove
```

اگر «با توکنِ درست» 401 گرفتید یعنی مقدارِ env دو طرف یکی نیست → بندِ ۳.

## ۵) مهم: در runtime توکن را حتماً بفرستید (حتی با وجودِ IPِ معتمد)

معافیتِ IP فقط برای نجاتِ build بود. در runtime ارسالِ توکن از BFF **الزامی بماند**، چون:

1. **rate-limitِ per-user:** بک‌اند فقط وقتی توکنِ داخلی معتبر باشد به هدرِ
   `X-Forwarded-For` شما اعتماد می‌کند و سهمیهٔ کاربرِ واقعی را جدا حساب می‌کند
   (OTP، کامنت، رأی، گزارش و…). بدونِ توکن، همهٔ کاربرانِ سایت یک سهمیهٔ مشترک
   می‌گیرند و «Too Many Attempts» برمی‌گردد.
2. **endpointهای نوشتنی** (sync و…) فقط با توکن کار می‌کنند — IP کافی نیست.
3. اگر روزی IPِ سرور عوض شود، توکن همچنان کار می‌کند (وابسته به IP نمی‌مانید).

## ۶) چرخشِ (rotation) توکن — بدونِ downtime

1. بک‌اند: مقدارِ فعلی را در `INTERNAL_API_TOKEN_OLD` می‌گذارد و توکنِ **جدید** را در
   `INTERNAL_API_TOKEN` → هر دو موقتاً معتبرند.
2. فرانت: env را به توکنِ جدید به‌روز و deploy می‌کند.
3. بک‌اند: بعد از تأییدِ فرانت، `INTERNAL_API_TOKEN_OLD` را حذف می‌کند.

## ۷) اگر build روی سرورِ دیگری اجرا شد

IPِ آن سرور را به بک‌اند اطلاع دهید تا به `TRUSTED_FRONTEND_IPS` اضافه شود
(لیستِ کاما‌جدا). یا توکن را به‌صورت **build secret** به مرحلهٔ build بدهید —
هر کدام کافی است.

## چک‌لیستِ فرانت

- [ ] مقایسهٔ اثرانگشتِ SHA-256 دو طرف (بندِ ۳) و اعلامِ نتیجه.
- [ ] تستِ سه‌گانهٔ curl از یک ماشینِ غیرمعتمد (بندِ ۴).
- [ ] اطمینان از ارسالِ توکن در **همهٔ** درخواست‌های runtimeِ BFF (بندِ ۵).
- [ ] توکن فقط در env سمتِ سرور — نه `NEXT_PUBLIC_*`، نه باندلِ کلاینت، نه ریپو.
- [ ] در صورتِ جابه‌جاییِ سرورِ build، اطلاع به بک‌اند (بندِ ۷).
