# نامه تحویل به تیم توسعه سایت — اجرای نقشه سئو (نسخه ۱۴۰۵/۰۵/۳۱)

مرجع کامل: سند «TamirOnline SEO Implementation Master Plan (FA)» مورخ 2026-08-22 — این نامه خلاصه اجرایی و تقسیم کار است؛ جزئیات Test Matrix و Rollback هر تیکت در همان سند است و **باید عیناً رعایت شود**.

## ۰) چیزی که از سمت پنل آماده شد (همین حالا در دسترس شماست)

سند در چند جا (G0-04، SEO-007، SEO-014، SEO-023) می‌گوید «پوشش خدمات باید source-of-truth تاییدشده داشته باشد». این منبع حقیقت ساخته شد:

```
GET https://panel.tamironline.com/v1/customer/seo/coverage
```

خروجی (JSON، public، کش ۱ ساعت):
- `cities[]`: فقط شهرهایی که **واقعاً تکنسین فعال دارند** — با استان، مناطق فعال (مثل ۲۲ منطقه تهران)، تعداد تکنسین و **لیست دقیق دستگاه‌های تحت پوشش همان شهر** (از مهارت واقعی تکنسین‌ها).
- `devices[]`: کاتالوگ کامل خدمات فعال.
- `coverage_data_complete`: اگر `false` بود یعنی داده پنل هنوز کامل نیست — **تا true نشده، این خروجی را وارد schema نکنید.**

مصرف در سایت:
1. **SEO-014:** به‌جای `areaServed: IR` در Service schema، دقیقاً شهرهای این خروجی را emit کنید. سمت سرور کش کنید (۱ تا ۲۴ ساعت) و اگر endpoint در دسترس نبود، از آخرین کش استفاده کنید — hardcode برنگردانید.
2. **SEO-007:** متن visible «مناطق/خدمات تحت پوشش» از همین منبع render شود تا متن و schema هرگز از هم فاصله نگیرند.
3. **SEO-023:** صفحه local فقط برای شهرهای موجود در این خروجی (فعلاً pilot تهران/کرج طبق تیکت) مجاز است.

### ۰.۱) نمای خدمت‌محور — برای صفحات خدمت و صفحات ترکیبی (به‌روزرسانی ۱۴۰۵/۰۶/۰۲)

همان endpoint حالا فیلد `services[]` هم دارد — دیگر لازم نیست خودتان `cities[]` را معکوس کنید:

```jsonc
"services": [
  { "id": 3, "name": "لباسشویی", "slug": "washing-machine",
    "province_count": 2, "city_count": 3,
    "provinces": [
      { "name": "تهران", "cities": [
          { "name": "تهران", "slug": "tehran", "technician_count": 12, "brands": "all" }
      ]},
      { "name": "خراسان رضوی", "cities": [
          { "name": "مشهد", "slug": "mashhad", "technician_count": 2, "brands": ["samsung"] }
      ]}
    ] }
],
"brands": [ { "name": "سامسونگ", "slug": "samsung" }, ... ]
```

قواعد مصرف:
1. **صفحه هر خدمت** (مثل «تعمیر لباسشویی»): بخش «استان‌ها و شهرهای تحت پوشش» را از `services[].provinces` render کنید (آکاردئون استان → چیپ شهر) + همین لیست در `areaServed` همان صفحه.
2. **صفحات ترکیبی خدمت+برند** (مثل «تعمیر لباسشویی سامسونگ»): فیلد `brands` هر شهر تعیین‌کننده است —
   - `"brands": "all"` → آن شهر برای همه برندها مجاز است.
   - آرایه slug → صفحه ترکیبی فقط برای برندهای داخل آرایه در آن شهر ساخته/لیست شود. برند خارج از آرایه در آن شهر تکنسین ندارد → صفحه نسازید (ادعای بدون ارائه = ریسک سئو و شکایت).
3. **صفحات ترکیبی خدمت+شهر** («تعمیر لباسشویی در مشهد»): فقط برای شهرهای داخل `services[].provinces[].cities`.
4. خدمتی که در `services` نیست یعنی در هیچ شهری تکنسین ندارد — صفحه‌اش را از لیست پوشش حذف/بدون claim نگه دارید.

نمای مدیریتی همین داده برای کارفرما در پنل: «افراد ← پوشش خدمات» (با فیلتر برند) — اگر درباره درست‌بودن داده سوال بود، همان صفحه مرجع مقایسه است.

### ۰.۲) عناوین مناطق تحت پوشش — `services[].titles` (به‌روزرسانی ۱۴۰۵/۰۶/۰۳)

هر خدمت آرایه `titles` دارد که کارفرما در پنل مدیریتش می‌کند (خدمات ← ویرایش خدمت ← «عناوین مناطق تحت پوشش»):

```jsonc
"titles": [
  { "prefix": "تعمیر",  "brand": "bosch",  "brand_name": "بوش",     "preposition": "در" },
  { "prefix": "خدمات",  "brand": null,      "brand_name": null,      "preposition": "برای" }
]
```

قاعده ساخت عنوان برای هر مکانِ تحت پوشش (استان/شهر/منطقه):

```
{prefix} {نام دستگاه} {brand_name?} {preposition} {نام مکان}
→ «تعمیر لباسشویی بوش در تهران» / بدون برند: «تعمیر لباسشویی در تهران»
```

- ترتیب آرایه = ترتیب نمایش در سایت.
- ردیف برنددار فقط برای مکان‌هایی معنا دارد که آن برند در `brands` همان شهر مجاز است ('all' یا شامل slug).
- ترتیب شهرها در `provinces[].cities` از قبل «مرکز استان اول» است — همان ترتیب را حفظ کنید.
- خدمت بدون تنظیم، یک ردیف پیش‌فرض `تعمیر … در …` دارد — یعنی همیشه می‌توانید به `titles` تکیه کنید.

## ۱) ترتیب اجرا — از سند منحرف نشوید

**Batch 0 (قبل از هر تغییر):** G0-01 تا G0-08 — freeze کردن baseline GSC، snapshot گیت، نقشه redirect های legacy (CSV ورژن‌دار)، دسترسی لاگ‌ها. بدون این‌ها هیچ تیکتی deploy نشود.

**Batch 1 — بنیاد URL و ایندکس (P1، اولویت مطلق):**
- **SEO-001:** رکورد ناموجود در routeهای داینامیک (سرویس/برند/ترکیب/مقاله/تاپیک انجمن) باید **404 واقعی** بدهد؛ الان 200 برمی‌گردد. redirect به هوم/بلاگ ممنوع.
- **SEO-002:** `/brands/BOSCH` و هر case variant → یک 301 به lowercase canonical. نرمال‌سازی بر اساس slug ذخیره‌شده، نه lowercase کورکورانه (slug فارسی/encoded نشکند).
- **SEO-003:** sitemap بلاگ بازسازی شود — الان child های 404 دارد و حداقل ۱۷۲ مقاله بیرون sitemap اند. منبع تولید = dataset مقالات، فقط URLهای 200/indexable/self-canonical.
- **SEO-004:** زنجیره‌های redirect یک‌مرحله‌ای شوند + همه لینک‌های داخلی مستقیم به URL نهایی. هیچ redirect داری backlink حذف نشود.
- **SEO-005:** لینک sitewide `/services/gas-stove` در ناوبری/فوتر → `/services/gaz`.

**Batch 2 — اعتماد، Schema و Performance (P1):**
- **SEO-007/008:** ادعاهای صفحه درباره ما (۲۰۰+ تکنسین، ۵۰,۰۰۰+ تعمیر، ۹۸٪ رضایت، ۱۵+ سال، «نصب») فقط با سند؛ Claim Register لازم است ← **منتظر تایید کارفرما (بخش ۳)**.
- **SEO-009:** صفحات Privacy/Terms واقعی + لینک در فوتر و کنار همه فرم‌های لید ← متن حقوقی از کارفرما.
- **SEO-010:** `SearchAction` در WebSite schema به `/search?q=` اشاره می‌کند که کار نمی‌کند — حذف کنید یا search واقعی بسازید.
- **SEO-011/012:** بهینه‌سازی تصاویر برند (srcset/WebP/lazy، شروع از `/brands/bosch`) + برنامه CWV موبایل (LCP≤2.5s، INP≤200ms) — هر تغییر با تست فرم/لید.
- **SEO-014:** areaServed از API پنل (بخش ۰).

**Batch 3 — Intent و معماری:** SEO-006 (مالکیت کوئری «تعمیر لباسشویی» به صفحه generic — بدون redirect/merge با صفحه Bosch)، SEO-013 (taxonomy بلاگ برای ۴۲۸ مقاله؛ ۲۵۶ مقاله orphan اند)، SEO-020 (لینک‌سازی داخلی به صفحات اولویت‌دار).

**Batch 4 — محتوا و On-page:** SEO-016 (یک Organization@id واحد در کل schema)، SEO-017 (نویسنده/بازبین واقعی مقالات ← roster از کارفرما)، SEO-018 (H1 برای FAQ/Pricing، توکن‌های خام در متا، title ترکیب دستگاه×برند)، SEO-019 (تمایز ۱۳۰ صفحه برند — فقط cohort اولویت‌دار، bulk ممنوع)، SEO-021 (width/height تصاویر)، SEO-022 (کنتراست موبایل).

**Batch 5:** SEO-015 (pagination و sitemap انجمن — page=0/999 الان 200 است)، SEO-023 (pilot تهران/کرج — **مشهد یا هر شهر تاییدنشده ساخته نشود**؛ از API پنل بخوانید)، SEO-024 (redirect یک‌مرحله‌ای http://www + ریشه‌یابی 5xx با لاگ).

## ۲) قوانین غیرقابل مذاکره (از سند)

1. هر تیکت = یک release قابل ایزوله با rollback از قبل نوشته‌شده.
2. هیچ URL سالمی نباید 404 شود؛ هیچ sitemap ای شامل redirect/noindex/404 نباشد.
3. هیچ claim/schema بدون معادل visible و بدون سند.
4. تست فرم/لید در هر release — سئو نباید یک لید را خراب کند.
5. مانیتورینگ روز ۱/۷/۲۸ طبق جدول بخش ۹ سند.

## ۴) نکته هماهنگی با پنل

- پوشش شهر/دستگاه در پنل از **تگ‌های پروفایل تکنسین‌ها** درمی‌آید؛ تکمیل این تگ‌ها در پنل مستقیماً خروجی API بخش ۰ را دقیق‌تر می‌کند.
- هر سوال درباره قرارداد API یا نیاز به فیلد جدید (مثلاً ساعات کاری per-city برای صفحات local) به تیم پنل اعلام شود — endpoint قابل توسعه است.
