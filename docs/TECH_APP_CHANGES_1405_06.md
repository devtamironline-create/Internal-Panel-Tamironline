# نامه به تیم اپ تکنسین — تغییراتِ سفارش (۱۴۰۵/۰۶)

این سند تغییراتِ سمتِ بک‌اند (که همین حالا اعمال و روی برنچ هستند) و
کارهای لازمِ سمتِ اپ را جمع می‌کند. بخشِ «قراردادِ API» را مبنای پیاده‌سازی
بگیرید؛ در نقاطِ اختلاف با اسنادِ قدیمی (`TECH_APP_API.md`,
`APP_ORDER_STATUS_LIST.md`)، این سند مرجع است.

---

## ۱) وضعیت‌ها — «شروع تعمیر» حذف شد 🔴

- وضعیتِ `repair_started` **کاملاً حذف شد**. همهٔ سفارش‌ها در فازِ کار روی
  «هماهنگ شده» (`coordinated`) می‌مانند؛ سفارش‌های قدیمی به‌صورتِ خودکار
  منتقل شدند.
- **اقدامِ اپ:** هر ارجاعِ hard-code به `repair_started` را حذف کنید
  (لیبل/بج/گروه همیشه از خودِ پاسخِ سرور می‌آید — hard-code نکنید).
- ترتیبِ نمایشِ وضعیت‌ها در فهرست/کشویی تغییر کرد: «در انتظار قطعه» و
  «در انتظار تأیید مشتری» **پیش از** «باز شده» می‌آیند. از ترتیبِ
  `allowed_transitions`/`options` سرور پیروی کنید.

---

## ۲) وضعیتِ «جدید» — فقط تماس 🟡 (کارِ اپ)

در وضعیتِ `new`، فقط دکمهٔ «تماس با مشتری» دیده شود؛ بقیهٔ سکشن‌ها مخفی.
هدف: مجاب‌کردنِ تکنسین به تماس برای تعیینِ وضعیت.

**فلوی لاگِ تماس (بک‌اند آماده است):** بعد از اینکه تکنسین روی شماره زد و
به اپ برگشت، سوالِ «نتیجهٔ تماس چه بود؟» را بپرسید و به این endpoint بفرستید:

```
POST /v1/technician/orders/{id}/call-result
Body: { "result": "coordinated" | "no_answer", "reason": "…" }
      reason فقط برای no_answer الزامی است (حداقل ۳ نویسه).
```

نتیجه در «تاریخچهٔ وضعیت»ِ پنل ادمین ثبت و دیده می‌شود. `coordinated` یعنی
بعدش تکنسین زمانِ مراجعه را ثبت می‌کند؛ `no_answer` سفارش را به همان وضعیت
می‌برد.

متن‌های راهنما در `app-config → messages` هستند
(`call_prompt_title`, `call_answered_label`, `call_no_answer_label`, …).

---

## ۳) مودالِ هماهنگیِ زمانِ مراجعه 🟡

- **سقفِ روز اضافه شد:** سفارشِ عادی حداکثر **۵ روز**، سفارشِ بازگشتی
  حداکثر **۳ روز**. سرور با ۴۲۲ enforce می‌کند و مقادیر در
  `app-config` آمده‌اند: `max_visit_days`, `max_return_visit_days`.
- **حدِ تغییر (۲ بار):** تکنسین حداکثر **۲ بار** می‌تواند زمانِ مراجعه را
  تغییر دهد (بارِ اولِ ثبت شمرده نمی‌شود). پس از آن سرور با **۴۲۳** پاسخ
  می‌دهد تا ادمین قفل را باز کند. در ریسورسِ جزئیات:
  `visit_reschedule_count`, `visit_reschedule_limit`, `visit_reschedule_locked`.
  وقتی `can_schedule=false` است دکمه را غیرفعال کنید.
- **UX:** انتخابِ روز را بهتر کنید (تقویم/کارت‌های روز به‌جای فهرستِ خام).
- **باگ:** دکمهٔ «هماهنگ کردن سفارش» باید تقویمِ انتخابِ تاریخ را باز کند
  (الان در برخی حالت‌ها باز نمی‌شود).

قرارداد:
```
POST /v1/technician/orders/{id}/schedule-visit
Body: { "visit_date": "Y-m-d", "visit_slot": 1|2|3|4 }   // یا { "clear": true }
```

## ۴) دسترسی سریعِ صفحهٔ اصلی 🟡 (کارِ اپ)

دکمهٔ «سفارش‌های باز» در سکشنِ دسترسی سریع به **«سفارش‌های جدید»** تبدیل شود.

---

## ۵) رسید انتقال 🟢

- عنوانِ دکمه: **«ارسال رسید انتقال»** (به‌جای «صدور/ثبت رسید انتقال»).
- **دیگر توضیح نپرسید:** توضیحِ رسید هنگامِ ثبتِ وضعیتِ «باز شده» گرفته
  می‌شود و رسید همان‌جا خودکار ساخته می‌شود. دکمهٔ «ارسال رسید انتقال»
  فقط بعد از یک مودالِ تأیید، پیامک را برای مشتری می‌فرستد (توضیحِ ورودی
  لازم نیست).

قرارداد (بدونِ بدنه):
```
POST /v1/technician/orders/{id}/transfer-receipt
```
سرور خودش رسیدِ ساخته‌شده در «باز شده» را پیدا و پیامک می‌کند.

---

## ۶) فاکتور در اپ 🟡

- فیلدهای **«اجرت»(hire)، «ایاب‌وذهاب»(transportation) و «تخفیف»(discount)**
  از فرمِ فاکتور حذف شوند. یک **قطعهٔ پیش‌فرضِ خالی** برای واردکردن ساخته
  شده باشد (تکنسین عنوان/خرید/فروش را پر می‌کند).
- بک‌اند این سه فیلد را دیگر لازم ندارد (اگر نیایند مشکلی نیست). مبلغِ کل
  از قطعات و `price_customer` محاسبه می‌شود.
- **عکس در همهٔ فاکتورها اجباری است.** برای سفارشِ **بازگشتی**، بک‌اند
  **عکسِ جدید** می‌خواهد (عکسِ سرویسِ قبلی کافی نیست) و بدونِ آن با ۴۲۲
  رد می‌کند (`device_img1`).

---

## ۷) سفارشِ بازگشتی 🟢/🟡

- **توضیحاتِ برگشتیِ ادمین** حالا در ریسورسِ جزئیات هست:
  `return_description` (فقط برای سفارشِ بازگشتی). آن را در مودالِ
  **«ثبت بررسی»** به تکنسین نشان دهید.
- دکمهٔ **«ثبت بررسی»** فقط وقتی نمایش داده شود که تکنسین **هماهنگ کرده**
  باشد (زمانِ مراجعه ثبت شده / وضعیت از فازِ هماهنگی گذشته).
- **سفارشِ بازگشتی وضعیتِ «رد»(Declined) ندارد** — نه در اپ (از قبل جزوِ
  گذارها نبود) و نه در پنلِ ادمین. تصمیمِ گارانتی/غیرگارانتی با «ثبت بررسی»
  است، نه ردِ سفارش.
- سقفِ «چند روز برای رفعِ مشکل» به **۶ روز** کاهش یافت
  (`max_estimate_days` در `app-config`)؛ در بررسیِ برگشتی هم `days ≤ 6`.
- هماهنگیِ مراجعهٔ سفارشِ بازگشتی سقفِ **۳ روز** دارد (بند ۳).

قرارداد بررسی:
```
POST /v1/technician/orders/{id}/return-review
Body: { "approved": true|false, "days": 1..6 (اگر approved), "note": "…" }
approved=true → گارانتی: فاکتورِ تکمیلِ مجدد پیش‌فرضِ ۰ (قابلِ تغییر).
approved=false → غیرگارانتی: فاکتورِ کاملِ جدید.
```

---

## ۸) فریزِ سفارش (قفل ادمین) 🟢

ادمین می‌تواند سفارش را «قفل/فریز» کند. در این حالت **هر تغییرِ سمتِ
تکنسین** با **۴۲۳** رد می‌شود (خواندن آزاد است). در ریسورس‌ها:
`is_locked` (لیست + جزئیات) و `lock_reason` (جزئیات). وقتی `is_locked=true`
یک بنرِ «این سفارش قفل شده» نشان دهید و دکمه‌های عملیات را غیرفعال کنید.

---

## ۹) پیام‌های خطا 🟡 (کارِ اپ)

خطای عمومیِ «اطلاعات وارد شده معتبر نیست» را با **پیامِ دقیقِ فیلدی** جایگزین
کنید. بک‌اند برای هر فیلد پیامِ فارسیِ روشن در ساختارِ استانداردِ ۴۲۲
برمی‌گرداند:
```
{ "message": "<اولین خطا>", "errors": { "<field>": ["<پیام فارسی>"] } }
```
`message` را مستقیم نشان دهید و در صورتِ نیاز `errors` را کنارِ همان فیلد.

## جمع‌بندیِ SLA (به‌روزشده)

| وضعیت | مهلت |
|---|---|
| جدید / در انتظار هماهنگی | ۱ ساعت از تخصیص |
| مشتری پاسخگو نیست | ۲۴ ساعت از تخصیص |
| هماهنگ شده | زمانِ مراجعه |
| در انتظار قطعه | ۵ روز |
| در انتظار تأیید مشتری | ۲۴ ساعت |
| معلق | ۷۲ ساعت |
| باز شده | ۱۰ روز |

همهٔ اعداد و متن‌ها در `GET /v1/technician/app-config` می‌آیند و بدونِ
انتشارِ نسخهٔ جدیدِ اپ قابلِ تغییرند — hard-code نکنید.
